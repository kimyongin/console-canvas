# 5개 프로젝트 × 25티켓 실사용과 UI/UX 간소화

2026-11-01 · **계획/미착수** · 상위 [#177](https://github.com/kimyongin/console-canvas/issues/177)

이번 문서는 다음 개발의 작업 계획이다. 샘플 생성·25개 사용자 티켓 작성·직접 테스트·제품 수정·설치 갱신은 아직 하지 않았다. 현재 설치 제품 0.46.0의 검증은 [이전 기록](ticket-first-0.46.md)이며 이번 실사용의 성공으로 재사용하지 않는다.

## 목적과 범위

개발자처럼 실제 화면을 가져오고 편집·주석·목표 확정·에이전트 구현·검토를 이어가며, 기능은 작동해도 번잡한 UI와 왕복을 찾아 제거한다. 화면을 더 많이 만드는 방식보다 중복을 없애고 가까운 위치에서 작업을 이어가는 방식을 우선한다.

GitHub의 상위1/개발7 이슈와 테스트 과정에서 **캔버스 안에 만드는 사용자 티켓25개**를 구별한다. 샘플은 각각 독립 소스 디렉터리·프로젝트 ID·실행법·수정 전 기준을 가진다. 새 외부 서비스 계정·유료 API는 필요하지 않게 구성한다. 제품 소스에 샘플 도메인/이름/고정 좌표에 맞춘 분기를 추가하지 않는다.

## 프로젝트마다 한 바퀴 반복

#178에서 샘플을 준비한 다음 아래 각 회차에서 **#179→#180→#181→#182→#183→#184**를 끝까지 수행한다. 5프로젝트의 기준선25개를 먼저 모은 뒤 한꺼번에 수정하는 방식은 사용하지 않는다.

| --- | --- | --- | --- |

| I3 | 칸반 업무 | 새 관점 평가·5티켓 → 개선/재설계 → 5사례 검증 → 가이드/설치 | 미착수 |
| I4 | 예약 관리 | 새 관점 평가·5티켓 → 개선/재설계 → 5사례 검증 → 가이드/설치 | 미착수 |

다음 회차는 직전 회차의 검증/설치 버전에서 시작한다. #179~#184는 회차별5개 완료 칸을 관리하며 I1 완료만으로 개발 이슈 전체를 닫지 않는다. #183은 현재5사례를 전후 비교하고 이미 끝난 프로젝트의 핵심 흐름을 스모크 확인한다. I5에서25사례 최종 집계를 한다. #184는 매 회차 수행하되 변경 없는 MCP/스킬·문서 항목은 불필요 재작성 대신 현재 일치를 확인한다.

### 매 회차의 근본 질문
- 이 기능/정보/버튼은 정말 필요한가? 없애거나 다른 흐름에 합쳐도 사용 목적을 달성할 수 있는가?
- 이 버튼이 정말 이 위치에 있어야 하는가? 빈도/중요도/대상과 가까운가?
- 목록은 이 형식·정렬·정보량으로 보여주는 것이 맞는가? 목록 자체나 목록→상세 구조를 바꾸는 편이 자연스러운가?
- 처음 쓰는 사람이 설명을 읽지 않고 현재 대상·다음 행동·결과를 이해할 수 있는가?
- 사람이 실제 목적을 편하게 달성하는가? 화면 이동·모달·재입력·작업 기억 부담을 제품 구조가 만들고 있지는 않은가?
- 현재 구조를 처음부터 다시 만든다면 지금처럼 만들겠는가? 기존 화면/메뉴/컴포넌트를 유지해야 한다는 전제를 버리면 어떤 구조가 더 나은가?

각 프로젝트마다 이 질문을 새로 던진다. 사용자 유형별 사전 지정 렌즈로 나눠 같은 체크리스트만 반복하는 뜻이 아니다. 필요하면 정보 구조·화면 구성·탐색·편집 흐름 전체를 다시 설계한다. 기존 UI 보존은 제약이 아니며 사용 목적·자료/복구·보안/권한·명시적 목표/승인만 보장한다. 액션 수는 근거 중 하나이며 편안함·발견성·인지 부담을 대신하는 유일 점수가 아니다. 변경 필요가 없으면 근거를 남기고 억지로 새 문제/재설계를 만들지 않는다.

‘이번 회차에 새 문제를 몇 개 찾았는가’가 목표는 아니다. 근본 질문·실제 관찰·대안·채택/유지 이유를 기록한다. 반복된 문제라면 이전 수정이 왜 부족했는지도 다시 묻는다. 작은 정돈에 한정하지 않고 필요하면 목록 형식·정보 구조·화면/내비게이션·편집/전달 흐름 전체를 바꾸고, 바뀐 계약에 맞춰 PRD/MCP/스킬/가이드·검증을 갱신한다.

## 매 회차 실제 사용하는 방법

1. 각 로컬 프로젝트를 실행하고 원본 화면에서 로그인 대체 상태·탭/메뉴·필터·로딩을 준비한다. 필요한 조작도 액션에 센다.
2. UI로 티켓을 생성하고 프로젝트/이름을 지정한 뒤 실제 수집 기능으로 화면을 붙인다. 티켓/캡처 JSON 주입이나 DB seed를 직접 사용 증빙으로 대신하지 않는다.
3. 선택·편집·주석·공통 설명으로 목적을 구체화한다. 같은 ID 목표를 확정하고 현재 편집과 고정 목표가 구별되는지 본다.
4. 에이전트에게 “이 프로젝트의 구현 대기 티켓 전부 구현해줘” 또는 명시한 ID 묶음으로 요청한다. 앱을 왔다 갔다 하지 않고 이미지/주석을 조회하고 실제 샘플 소스를 구현·검증·기록한다.
5. 결과를 같은 대화에서 비교한다. 테스트 역할로 확정한 가상 목표/검토와 실제 사람의 승인을 구별한다. 자동 검사 성공만으로 실제 승인/done을 만들지 않는다.
6. 중간에 이름 변경/전환·재열기/취소·undo/redo·휴지통/복구·공유 철회/오류를 교차 배치한다. 같은 부가 검사를 모든 25행에 중복 강제하지 않는다.

이미지 시안 탐색 경로는 사용 가능한 실제 에이전트 도구로 별도 실행하고 현재 결과 직접 확정과 구별한다. 도구/환경이 안 되면 fixture 시안을 실제 생성으로 표시하거나 미실행 새 대화를 통과로 체크하지 않는다. 관련 실행 조건과 검증 항목은 열린 상태로 남긴다.

## 액션·사용성 기록

각 사례에 시작/완료 상태, 기준 버전, 뷰포트·수집 범위, 원본/편집 사진, 실제 CC-ID, 단계별 경로, 발생 문제를 기록한다. 보고서에는 **기준선 → 개선안 → 재실행 결과**가 연결돼야 한다.

- 클릭, 메뉴 펼치기/닫기, 링크 이동, 페이지/패널/모달 전환을 기록한다. 클릭으로 전환이 일어난 경우 총수에는 클릭1회로 세고 전환 지표를 별도 표시해 이중 합산하지 않는다.
- 앱↔에이전트 대화 왕복을 기록한다. 문장/필드 입력은 입력1회, 제출은 제출1회로 세며 글자 수는 별도다. 키보드로 메뉴를 여는 동작도 포함한다.
- 시스템이 완료되지 않아 추가한 재시도, 대상 재선택, 불필요 재확인, 동일 내용 재입력, 헛클릭은 따로 구분한다. 스크롤은 연속된 한 구간 이동을1회로 기록하고 목적지를 기록한다.
- 최초 MCP/스킬·프로젝트 공유 설정과 반복 작업을 나눠 센다. 최초 연결 비용을 숨기거나 반복 경로에 섞어 감소율을 부풀리지 않는다.
- 25개 평균만으로 긴 최악 경로를 가리지 않는다. 유형/프로젝트별 총수와 메뉴·화면/앱 왕복, 막힌 단계, 필요한 확인을 비교한다.

### 채택 기준

중복/불필요 탐색이 있던 경로는 제거 뒤 실제로 줄어야 한다. 모든 기능에 임의의 클릭 수/감소율을 강제하지 않는다. 행동이 늘면 이유와 사용자 이득을 명시한다. 액션이 줄어도 대상 식별·기능 발견성·내용 가독성·키보드/포커스·취소/복구·저장/권한·목표/승인 보호가 나빠지면 수정안을 되돌리거나 다시 설계한다.

## 우선 감사할 군더더기

| 영역 | 감사 후보 | 판단 원칙 |
| --- | --- | --- |

## 일괄 요청 검증

각 프로젝트의 5티켓을 대상으로 요청 시점 ID 집합·프로젝트·goal_id/revision을 고정한다. pagination 누락, 동명·프로젝트 모호성, rename/재정렬·새 티켓 추가, 준비 중/blocked/휴지통/완료 상태, 같은 영역 충돌·부분 실패·의존 작업 보류를 검사한다. 실패한 작업 때문에 독립 작업이 불필요하게 멈추지 않게 하고 티켓별 결과를 요약한다.

작업 전후 조건과 실제 소스 diff·화면·반응형/기능 검사를 티켓에 연결한다. 무단 프로젝트 확장, 목표 자동 선택, 이미 끝난 작업의 무조건 재실행, 일괄 요청을 일괄 승인으로 해석하는 동작은 허용하지 않는다. 필요한 근거 없이 bulk MCP API나 복잡한 큐/진행 대시보드를 새로 만들지 않는다.

## 검증·배포

- 공통 UI는 직접 브라우저 사용과 npm run check, 바뀐 MCP는 공식 SDK로 확인한다. 수집·파일/IPC·저장 flush·종료 등 변경한 Electron 경계를 추가 검증한다.
- 같은 원본 상태/뷰포트/범위의 사진과 복제본을 비교한다. >=95% 기준과 차이/허용오차를 유지하고 새 샘플 통과를 모든 사이트 보장으로 확대하지 않는다.
- 실제 OS 창/수집·직접 UI·SDK·가상 fixture·별도 에이전트 대화 검증의 증빙을 구별한다. 잠금/권한/도구 제약으로 못 한 항목은 성공으로 처리하지 않는다.
- 최종 PRD·가이드 실제 캡처·MCP/스킬을 동기화하고 기존 자료/개인 스킬 백업·정상 종료 후 같은 Apple 서명으로 설치 앱을 갱신한다. 정상 재실행 뒤 화면·자료·설치 스킬·새 MCP 연결과 단일 앱 실행을 확인한다.
- 사용자 자료·로그인/키·실제 사용자 캡처는 저장소에 올리지 않는다. 실행 로그/사적 증빙은 ignored local/에 보관하고 보고서에 요약한다.

기존 #7/#68/#73/#152 잔여는 별도 유지한다. 제거한 스냅샷/분기·앱 직접 AI/인증·후보 갤러리·Chrome 확장을 재도입하지 않는다.


## 사용자가 지정한 구체 사례 · 2026-11-01

주석 창의 ‘배치 의도 제안’, ‘좁은 화면에서는’ 문장 선택 버튼과 상시 설명도 군더더기다. 이 정도 작성 힌트는 입력칸 placeholder로 충분하다. 필드 label·현재 대상·필수 저장/오류 피드백은 유지하고, 반복 가이드·추천 문장/칩·도움말 카드로 입력 영역을 둘러싸지 않는다. 입력을 시작하면 안내가 자연스럽게 사라지는 구성을 기본으로 한다. 이 기준은 주석뿐 아니라 다른 폼·빈 상태·모달 감사에도 적용한다. 전체25사례는 아직 미착수이며 이 구체 사례만 선행 수정한다.
