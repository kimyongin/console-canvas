# 가져오기 정밀도 · 0.24.1

2026-10-29 · #67 · FR-01/10/11 · AC-66

## 수정한 원인

1. 이름 있는 OpenType 기능 정의가 누락됐다. `font-variant-alternates: styleset(...)`은 이름을 참조하므로 폰트 파일과 계산된 속성만으로 같은 글리프를 재현할 수 없다. `@font-feature-values`, `@font-palette-values`를 CSS 계층·프레임 병합·Inspector로 읽은 스타일시트에서도 보존한다. font-palette/size-adjust/synthesis/language-override 속성도 수집한다. [MDN 공식 설명](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/%40font-feature-values).
2. 끝이 잘린 PNG도 Blink가 `decode()` 성공·complete·naturalWidth 정상으로 보고할 수 있었다. 실제 GitHub 캡처의 해당 PNG에는 IEND가 없었고 하단 스캔라인이 흰색으로 빠졌다. 수집 시 해당 데이터를 완전한 리소스로 채택하지 않는다. 이전 문서도 원본 촬영 픽셀이 있으면 IMG 한 개만 보완하며 HTML·노드·편집·스냅샷을 다시 쓰지 않는다. 화면 전체를 이미지로 평탄화하지 않는다.

## 같은 원본의 수정 전후

기존 RGB 최대 채널 차이 **16/255** 판정과 비교 영역을 그대로 유지했다. 추가로 차이 8 이하와 RGB 완전 동일 비율을 기록한다. 마스크·허용 오차 확대·비교 높이 축소를 사용하지 않았다.

MDN은 실제 새 캡처에서 이전 수집기가 빠뜨리던 폰트 기능 정의만 제거한 대조군과 정상 캡처를 비교했다. 같은 원본 사진·폰트 바이트·DOM·뷰포트이며 폰트 정의의 효과를 분리한다. GitHub는 0.24의 같은 저장 캡처·원본/복제 PNG와 새 렌더를 비교했다.

| 경로·영역 | RGB16 이전 → 개선 | RGB8 이전 → 개선 | RGB 완전 동일 이전 → 개선 |
| --- | ---: | ---: | ---: |
| 내장 MDN 초기 화면 | 96.99% → **99.89%** | 96.70% → **99.88%** | 96.43% → **99.87%** |
| 내장 MDN 문서 | 97.68% → **99.97%** | 97.46% → **99.96%** | 97.23% → **99.95%** |
| Chrome MDN 초기 화면 | 96.79% → **99.30%** | 96.49% → **99.24%** | 96.18% → **99.16%** |
| Chrome MDN 문서 | 97.92% → **99.97%** | 97.71% → **99.96%** | 97.51% → **99.95%** |
| 기존 내장 GitHub 문서 | 96.59% → **99.81%** | 96.57% → **99.81%** | 96.56% → **99.31%** |

MDN은 내장 1440×1000·Chrome 1600×1100, 문서 높이 5,245px다. GitHub는 폭 1440·문서 높이 5,216px다. 별도로 GitHub를 새로 가져온 결과도 초기 99.92%·문서 99.82%를 확인했다. 이번 수정으로 모든 웹사이트가 99% 이상이 됐다는 뜻은 아니다.

기존 10개 사이트 원본을 유지한 회귀 비교는 내장/Chrome 각각 10/10이 95% 이상이다. 이전 MDN 캡처에는 누락된 폰트 이름 정의가 없으므로 재열기만으로 이를 만들어내지 않는다. 재수집한 MDN의 개선과 구별한다. 기존 Chrome 다음의 문서 96.46% 등 남은 동적/이미지·렌더 차이는 여전히 있다.

비공개 증빙: `local/precision-mdn{,-before-result}/`, `local/precision-chrome-mdn{,-result,-before-result}/`, `local/precision-github-replay/`, `local/precision-github-fresh/`, `local/precision-{native,chrome}-regression/`. 각 비교에 원본·복제·차이 PNG, 수집 JSON·좌표·측정값과 편집/저장 확인을 보존했다. 실제 자료는 커밋하지 않는다.

## 검증·배포

가상 회귀는 CSS 계층/다른 프레임의 폰트 기능 이름, 디코딩 가능한 불완전 PNG 거부, 기존 캡처의 원본 데이터 무변경 복구를 검사한다. 최종 `npm run check`는 Python 43·Node 40·Chromium 466개와 독립 HTML·포인터 검사를 통과했다. 캡처 품질 회귀 42개를 포함한다. 실제 Chrome 확장 제품 통합 62개와 정확한 배포 런타임의 공식 MCP SDK 22+17개, sandbox·원본 무변경·정상 종료/재실행·주석/분기/휴지통 보존을 통과했다.

공식 Electron SHA-256·앱 서명·DMG 체크섬과 런타임/스킬 ZIP의 바이트 일치를 검증했다. 사용자 앱의 저장·편집 파일 내보내기·정상 종료 후 앱/전체 프로필/스킬/확장을 백업하고 0.24.0→0.24.1을 설치·재실행했다. 전후 편집 파일은 생성/갱신 시각을 제외한 HTML·364개 요소·편집·주석·활동·추가 설명·스냅샷 3개 전체가 같았다. 실제 UI에서 0.24.1과 스킬 자동 갱신을 확인했고 새 공식 SDK 클라이언트로 설치 스킬을 통해 guide 0.24.1·사용자 화면·요소·주석·스냅샷을 읽기 전용으로 조회했다. 사용자 문서에 테스트 편집은 적용하지 않았다.

일반 Chrome은 동일 ID/설치 경로로 0.24.1을 활성화했다. 사용자 확장 문서 직접 열람은 기존 URL 정책 제한을 우회하지 않았으며 별도 프로필의 실제 확장 수집/재열기 검사와 구분한다. 설치는 백업을 동반한 직접 교체이며 업데이트 버튼의 자기 교체 흐름을 다시 검증한 것은 아니다.

검사 로그는 `local/precision-final-check.log`, `local/precision-packaged-sdk.log`, `local/precision-chrome-product/`, 실제 사용자 보존 증빙은 `local/deployment-0241-backup/`다.
